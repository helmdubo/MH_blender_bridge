# ADR v4 — mh_asset_io: нативный FBX-кодек на ufbx / ufbx_write

Статус: **ACCEPTED (roadmap)**. Реализация — исключительно срезом S7
(`09_v4_agent_slices.md`), после приёмки S6. Ничего в S3–S6 этот ADR не
меняет; до S7 действует 08 §4.1 как записано (штатный `io_scene_fbx` —
пинованная стадия 2). Норматив остаётся один — 08; этот документ фиксирует
решение, границы и отвергнутые альтернативы.

## Контекст

- Студийный floor — Blender 4.5 LTS+; новый C++ FBX-импортёр Blender
  построен на `ufbx` (в 4.5 experimental, в 5.0 — default). Судьба legacy
  Python `io_scene_fbx` в 5.x — вне нашего контроля; 08 §4.1 уже пинует
  выбор импортёра оператором, а не дефолтом пользователя.
- Внешний анализ (owner-attachment, 2026-08) предложил связку
  `ufbx` (decoder) + `ufbx_write` (encoder) с собственной канонической
  моделью сцены. Ядро анализа совпадает с нашей архитектурой: FBX — кодек
  транспорта, модель — своя (симметрично `FMHSceneIR` на UE-стороне и
  parse-truth стадии 0 в 08 §4.1).
- `ufbx` зрел (production в самом Blender); `ufbx_write` — WIP с
  явным предупреждением о breaking changes и открытыми round-trip
  дефектами (арматуры — вне нашего диалекта, но индикатор зрелости).

## Решение

Отдельный компонент **`mh_asset_io`**: нативный Python-модуль (.pyd/.so;
nanobind или pybind11; `ufbx`/`ufbx_write` vendored на зафиксированных
коммитах, без network fetch на сборке). Ядро Blender-agnostic: знает только
собственную модель сцены (по смыслу общую с `FMHSceneIR`), обмен с bpy —
исключительно bulk-буферами (`foreach_get`/`foreach_set`, NumPy), никаких
пер-вершинных Python-циклов.

Две фазы с независимыми гейтами:

- **Фаза A — импорт (низкий риск).** Декодер на `ufbx` заменяет ТОЛЬКО
  стадию 2 из 08 §4.1. Стадии 0/1/3/4, оператор, предусловия, откат дельты
  и non-goals не меняются. Выгода: плейсхолдерные материалы не возникают
  вовсе (слоты назначаются каноническим материалам до создания мешей),
  зависимость от legacy Python-импортёра исчезает.
- **Фаза B — экспорт (по отдельному owner-gate).** Encoder на `ufbx_write`
  НЕ начинается без явного owner-решения о зрелости библиотеки
  (стабильность API + статик round-trip на нашем диалекте). Обязательный
  validator: `write → чтение обратно через ufbx → сравнение моделей`;
  отказ validator'а = отказ экспорта (файл не публикуется). Текущий
  Python-экспортёр остаётся fallback до доказанного полного паритета.

## Отвергнуто (нормативно, не пересматривается этим ADR)

- **Custom properties / паспорт в FBX** — регрессия против v4: FBX остаётся
  обычным, без `mh_*`-метаданных (08 §4, поправки owner, purge S1).
  Семантика живёт в именах, `.material`/`.composite` JSON и receipts.
- **FBX mesh instancing как транспорт размножения** — домен композита
  (name-referenced размещения, 08 §6), не FBX.
- **Линковка к внутренностям Blender (BKE_*)** — форк, привязанный к
  сборке; стабильного C++ plugin API у Blender нет.
- **`ufbx_scene`/FBX-структуры как модель пайплайна** — модель всегда своя;
  кодек заменяем.
- **Расширение FBX-диалекта** — S7 не добавляет нормативных полей; диалект
  задан 08 §4 и меняется только поправкой owner.

## Гейты и acceptance (детально — 09 §S7)

Фаза A: side-by-side паритет с §4.1-импортом на golden-наборе (та же
классификация узлов, слоты, трансформы; геометрия в заданном допуске);
bpy-гейты обеих веток; packaging wheel'ов в Blender Extension для
поддерживаемых платформ. Фаза B: FBX от encoder'а читается S5-импортёром UE
и §4.1-импортом идентично выходу текущего экспортёра; validator обязателен;
fallback сохраняется до полного паритета.

## Последствия

- До S7 ничего не меняется; 08 §4.1 — действующий контракт импорта.
- Появляется нативная сборочная матрица (Windows обязательно; прочие
  платформы — по floor студии) — цена, принятая осознанно.
- После фазы A судьба legacy Python-импортёра Blender перестаёт быть
  нашим риском; после фазы B диалект FBX на выходе полностью
  детерминирован нашим кодом.
