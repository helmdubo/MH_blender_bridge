`OPEN-V4-18`**. Первоначальные `OPEN-V4-12`–`OPEN-V4-16` решены owner в

## База и границы

## Выполненная ориентация

1. Три независимых read-only аудита разложили:
   - текущие scanner/resolver/analyzer/Ledger/composition seams и полный
     Ledger removal surface;
   - stock UE 5.7 `SQLiteCore`, Asset Registry API и будущие build boundaries;
   - S4 schema/state machine, dependency/GeneratedAssets/event semantics и
     acceptance-гейты.
2. Подтверждено, что `IMHSourceResolver`, `IMHChangeDetector` и
   `MHSourceComposition` позволяют локализовать SQLite backend без зависимости
   importer/compiler от SQLite. Существующий scanner уже даёт reusable
   classifier, allowlist, stable double-read/hash, alias/root protection,
   quarantine и deterministic duplicate ordering.
3. Точка startup после `AssetRegistry.OnFilesLoaded` существует в
   `UMHSourceImporter`. Material/Composite публикуются через общие low-level
   atomic writers, однако Adopt и Automation также вызывают их напрямую:
   publish recorder нельзя без решения навесить только на UI/subsystem wrapper.
4. Stock UE 5.7 предоставляет editor-совместимый `SQLiteCore` с
   `FSQLiteDatabase`/prepared statements/transactions/user-version/integrity.
   Будущая реализация потребует private module dependency и явный plugin
   dependency, поскольку `SQLiteCore` не enabled-by-default. Runtime/Engine
   менять не требуется.
5. Сформирован acceptance-план `Mimir.V4.ProjectIndex`: logical
   schema/rebuild parity, 10k resolve с counting scanner, move identity,
   rename/orphan, duplicate transitive blocking, exact-five GeneratedAssets,
   injectable self-publish classification и static Ledger purge.

## Нормативные блокеры

Первоначальные блокеры ниже решены нормативным коммитом `ca006b2`:

- `OPEN-V4-12`: universe/precedence/retention состояний Project Index,
  generation/schema recovery и точный rebuild-identical subject;
- `OPEN-V4-13`: источник applied raw state после Ledger и coverage/carrier
  GeneratedAssets для texture/mesh/material/composite;
- `OPEN-V4-14`: exact dependency edge/role set, FBX-slot phase и политика
  ambiguous owner;
- `OPEN-V4-15`: граница S4/S6 для watcher, lifecycle self-publish token и
  deterministic probable-rename batching/retention;
- `OPEN-V4-16`: rebind action и измеримая метрика «сильно разошедшегося»
  orphan content.

Все вопросы оформлены в `docs/QUESTIONS.md` с временными fail-closed
правилами. Согласно инварианту 09 исполнитель не выбрал internal state/bytes,
которые влияют на обязательные S4 rows, diagnostics и acceptance.

После повторного чтения и начала разложения реализации два независимых аудита
обнаружили ещё две неполные ветви уже ратифицированной проекции:

- `OPEN-V4-17`: словарь GeneratedAssets не задаёт status валидного
  единственного claim при source key `ambiguous` или `invalid`;
- `OPEN-V4-18`: Texture обязана иметь шесть tags, но её carrier не содержит и
  норматив не определяет значение/hash-domain `MH.AppliedHash`.

Самостоятельно использовать `stale` для non-unique source либо
`MH.AppliedHash = MH.SourceHash` исполнитель отказался: обе трактовки меняют
нормализованный dump/receipt contract и требуют owner-решения.

До обнаружения повторного STOP завершены только две однозначные части:

- `75d6b27` регистрирует три уже ратифицированных S4 diagnostic codes и
  обновляет golden counts до `45 E / 13 W`;
- `36f854c` удаляет Ledger-only `ContentRoot` setting после нормативного purge
  Ledger.

Параллельный Ledger-removal delta остановлен до композиции с индексом и не
является готовой/запушенной implementation частью.

   guarded build и `BuildPlugin -StrictIncludes`, затем заменить эту
   STOP-квитанцию финальной READY-квитанцией.
