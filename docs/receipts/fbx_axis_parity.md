# Квитанция — осевой паритет меш-транспорта (взорванный коттедж)

Дата: 2026-08-31
Ветка: `fix/fbx-axis-parity`
Исполнитель среза: Lead (по слову owner «ДЕЛАЙ»)
Статус: **READY FOR OWNER FIELD TEST (только UE Import Changed)**

## 1. Полевой дефект

Первый полностью собранный импорт коттеджа дал «взорванный» дом: каждый
меш стоит на своей позиции, но повёрнут на 90° вокруг Z собственного
пивота (плюс зеркальность перестановки осей). На симметричном контенте
(gaz53) дефект маскировался; рядом с Interchange-эталоном стал очевиден.

## 2. Диагноз (доказан численно)

- Узловые TRS и весь конвейер Blender→файлы→resolved-план верны
  (сверено: 851 лист, 0 расхождений >1 см; owner подтвердил
  garage_gate: Blender (7.875, 1.35, 1.009) м ↔ UE (787.5, −135, 100.9)
  см — ратифицированная (x, −y, z)×100 конвенция).
- Геометрия FBX верна (реимпорт в Blender сходится с definition).
- Дефект — в боевом `FMHFbxSceneTranslator`: он запекал
  `EvaluateGlobalTransform()` сырым, тогда как канонический
  Blender-экспорт (`axis_forward='X'`) вкладывает в каждый корневой узел
  осевую конверсию RotZ(−90°), а контрольные точки оставляет сырыми.
- Ратифицированная истина уже была закреплена: фикстура
  `golden/fixtures/axis/axis_probe.fbx` и `MHAxisProbeTest` требуют
  контрольную вершину Blender (0.37, 0.11, 1.93) м → UE (37, −11, 193)
  см — но тест покрывал только диагностические бэкенды
  (`FMHFbxBackend`, читающий control points сырыми), а не боевой
  translator. R1-контракт (`make_axis_bundle.py`, RISK_RESULTS) писал
  прямо: «отрицание Y обязан выполнить импортёр UE (convert_scene=True)»
  — сток-семантика, которую SDK-translator при появлении не воспроизвёл.

## 3. Реализация

`MHFbxSceneTranslator.cpp`: хелпер `CanonicalAxisUnwind()` (RotZ(+90))
домножается слева на `EvaluateGlobalTransform()` в двух местах — bake
геометрии (`ReadGeometry`) и node `GlobalTransform` (сокеты, коллизия,
bounds). Легитимность константы обеспечена существующей fail-closed
валидацией canonical transport: translator принимает только файлы ровно
нашей осевой пары.

`MHStaticMeshImportData.h`: `MHStaticMeshImporterVersion` 4 → 5 — каждый
меш, применённый версией 4, повёрнут на 90° и пересобирается одним
штатным Import Changed.

Тестовые фикстуры (`MHStaticMeshImporterTest.cpp`): синтетические FBX
писали узлы без экспортной конверсии — добавлен
`ApplyCanonicalExportConversion()`, зеркалящий реальный транспорт;
контрактные ожидания сокетов/коллизий не менялись.

**Не менялись**: Blender-экспортёр, Blender-импортёр, форматы, golden
(фикстура и вектора байт-в-байт), реестры кодов, аддон. Полный
переэкспорт `.mesh.fbx` НЕ требуется.

## 4. Red → green

Новый постоянный тест `Mimir.C0.R1.TranslatorAxisParity` — боевой
translator против ратифицированной golden-фикстуры:

- RED: `expected (37, -11, 193), nearest (11, 37, 193), delta 54.59 cm`
  — точная сигнатура RotZ(+90)-загрязнения;
- GREEN после фикса.

Полевое подтверждение диагноза (одноразовые пробы, не в коммите):
экспорт окна тремя осевыми парами через translator показал, что только
identity-чтение соответствует композитной конвенции; выбран фикс на
UE-стороне, потому что он не требует переэкспорта и приводит код к уже
ратифицированному R1-контракту.
