# Квитанция V5-S6.5.1 — Endpoint cache

## 1. Итог

Срез выполнен в ветке `v5/s6.5.1-endpoint-cache` от `c9e3912`.
Работа ограничена editor-путём плагина `ue/MimirComposite` и этой
квитанцией. Engine, runtime/cook-путь, формат `.composite`, план,
подписи, `golden/` и `reference/` не изменялись.

`FMHCompositeDefinitionEntry` теперь содержит требуемую weak-карту
`TMap<FMHResourceKey, TWeakObjectPtr<UObject>> Endpoints`. Актор держит
lease на shared entry вместе с immutable-графом. Первый доступ выполняет
прежний строгий `MHLoadAppliedResource`, успешный canonical
`UStaticMesh` кладётся в карту, а hit проверяет только живость, класс и
canonical object path. Мёртвый либо потерявший identity weak удаляется и
перерезолвится только для своего ключа; неуспех не кэшируется.

Мёртвый `MHBuildRandomSourceClosure` на definition hit удалён. Живой
`MHValidateAppliedCompositeRoot` и нормативный двухступенчатый lookup по
root сохранены.

## 4. Реализация

Коммит: `1f9cec5 Cache placement endpoints in shared definitions`.

- значения subsystem-map переведены на shared entry, чтобы placements
  одного definition использовали одну endpoint-карту;
- `AMHCompositeActor` хранит transient C++ lease на entry; сериализация и
  persisted authority не добавлялись;
- editor placement compiler принимает optional entry. Нормальный
  `PostRegisterAllComponents`-путь использует cache, а editing/fallback
  без admitted entry остаётся на прежнем cold loader;
- cache admission выполняется только после прежнего resource resolution
  и проверки `UStaticMesh`/canonical path;
- failed resolution не попадает в карту;
- существующая `MHNotifyGeneratedResourceChanged`-воронка без изменений
  удаляет entry по dependency и синхронно пересобирает зависящие actors;
- новая точка создания компонентов не добавлялась; `OnConstruction`,
  orphan-union и appearance fast-path не менялись.

## 10. Вопросы

1. **Контекст:** `FMHResourceKey` не имеет kind для actor class, тогда как
   ратифицированная endpoint-карта имеет точный тип
   `TMap<FMHResourceKey, TWeakObjectPtr<UObject>>`. Actor-leaf продолжает
   использовать существующий `ActorClassRegistry` и `TryLoadClass`.
   **Вопрос:** нужен ли отдельный будущий cache для actor classes?
   **Временное fail-closed допущение:** в S6.5.1 кэшируются только managed
   resource endpoint’ы, представимые canonical `FMHResourceKey`; семантика
   actor registry и enum не расширяются без отдельного решения Lead.
